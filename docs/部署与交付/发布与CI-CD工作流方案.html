学习系统如何从本地代码发布到线上？

针对 Vue 3 + FastAPI + MySQL 的单人毕设，比较手动发布与 GitHub CI/CD，并给出一条适合现有博客、SyncRTC 共用服务器的实施路线。

推荐结论方案比较现有项目发布流程构建与打包服务器准备迁移与回退实施顺序

推荐结论

首版采用“自动 CI + 手动触发 CD + 自动部署脚本”。本地只负责开发和测试；GitHub Actions 在合入 main 后构建、测试、生成带提交 SHA 的发布包。你确认要上线时，在 GitHub 点击部署；CD 下载刚才通过 CI 的同一份产物，经受限 SSH 账号上传并执行服务器发布脚本。

这仍然是 CI/CD：检查、打包、上传、替换、健康检查和失败回退都由流水线执行，人工只决定何时将哪一个已验证版本发布到生产。系统稳定并演练过回退后，可以把 CD 改为“main 的 CI 成功即自动发布”。

本地功能分支→PR 自动 CI→合入 main→CI 产物→手动触发 CD→线上验证

2026-10-27 已建立独立 Git 仓库，采用 main + 功能分支；GitHub Actions 与自动发布仍待实施。

四种做法怎么选

做法适合场景主要代价本项目判断
本地构建后 SCP 上传首次部署、临时演示依赖本机环境；漏传文件、传错版本或误覆盖较难追溯只作首次联调或应急路径
服务器 git pull 后现场构建很小的个人原型生产服务器要装构建工具；构建结果依赖当时的网络和环境，也难保证与 CI 验证的是同一产物不作为正式发布方式
GitHub CI 产物 + 手动 CD单人毕设、共用服务器需要一次性配置 Actions、受限 SSH 账号和发布脚本推荐首版可追溯，且上线时间由你控制
GitHub CI 成功后自动 CD流程成熟、变更频繁合入 main 就可能立即碰到真实数据库和线上用户回退和迁移规则演练后再启用
Docker 镜像 + Compose需要镜像化复现、已有容器运维习惯增加镜像仓库、容器网络和数据卷管理；还需与现有 Nginx/服务协调可扩展选项，首版无须引入

与现有博客、SyncRTC 的关系

博客

GitHub main 上的 Blog CI 测试并构建两个 Vue 前端，打包发布产物；Blog CD 在 CI 成功后下载对应产物，通过 SSH 发布并做公网只读检查。这个“同一产物贯穿 CI/CD”的做法可以借鉴。

SyncRTC

SyncRTC CI 将 C++ 服务构建、测试并打包；CD 接收 CI 产物，也提供手动触发入口。学习系统后端是 Python，通常不需像 C++ 那样编译为 ELF，但仍需锁定依赖、测试和制作发布包。

以上描述依据仓库工作流文件，不代表已检查今天服务器上的实际部署状态。新项目与它们独立建库、目录和服务，不能复用博客或 SyncRTC 的发布脚本。

推荐的 GitHub 工作流

  1. 开发：在独立仓库的 feat/* 分支写代码，PR 指向 main。单人新项目先用 main + 功能分支即可；若以后建立长期 develop，再按对应分支规则发布。
  2. PR CI：安装锁定依赖；运行前端类型检查、构建，以及后端测试；用临时 MySQL 检查迁移和关键接口。PR 任务不持有生产 SSH 密钥。
  3. main CI：对准确的 commit SHA 重跑门禁并制作发布包，写入 SHA、构建状态、依赖版本和 SHA-256 校验值，上传为 GitHub Actions artifact。
  4. 手动 CD：指定已通过 CI 的提交/运行记录；只下载这个运行生成的产物，核对来源与校验和，拒绝 PR 产物或 SHA 不一致的包。生产部署同一时刻只允许一个任务执行。
  5. 服务器发布：上传到临时目录，备份受影响数据，执行已审核的数据库迁移，将新版本放到独立 release 目录，切换当前版本，重启 FastAPI 和评分 worker。
  6. 验收：检查本机 /api/health、公网用户端和管理端、登录权限、关键只读接口及服务日志；失败则切回上一版应用代码并保留排障证据。

GitHub 官方文档确认：artifact 可保存构建产物；Environment 可限制生产部署。若未来改用 workflow_run 自动触发，要额外核对触发来源，因为后续工作流可接触生产密钥；见 GitHub 的安全说明。

“编译打包”对各组件意味着什么

组件CI 做什么服务器收到什么
Vue 用户端/管理端npm ci、类型检查、测试、vite build静态 dist/ 文件，由 Nginx 服务；不需要服务器再装 Node.js 构建。Vite 构建说明
FastAPI API 与评分 worker安装固定版本依赖、测试、打包 Python 源码和依赖清单按发布版本建立独立 Python 虚拟环境并启动 systemd 服务；无需把源码“编译成 Go/C++ 那样的二进制”
MySQL 表结构在临时库验证迁移能从上一结构升级版本化迁移文件；生产数据本身不进入发布包，生产执行迁移前先备份
DuckDB/Parquet 分析测试清洗与聚合脚本，使用小样本核对结果分析脚本随版本发布；真实 Parquet 数据放独立数据目录，不随代码覆盖
模型 API key、数据库密码只在测试中使用替身或测试密钥保存在服务器受限环境配置；绝不进入前端包、Git 仓库或发布 artifact

首次实现可以让 CD 在服务器上依据锁定的依赖文件创建新版本的虚拟环境。若将来遇到网络或原生依赖导致发布不稳定，再升级为 CI 产出与服务器系统兼容的 Python wheel 包；目前无需先引入镜像仓库。

一次性准备与日常发布分开

首次准备，人工完成并记录

检查服务器 CPU、内存、磁盘和端口；配置 learn.gentleyun.cn 的 DNS、HTTPS 与独立 Nginx 虚拟主机；创建独立 MySQL 库/账户；准备部署目录、备份目录、受限 SSH 账号，以及 API、worker 的 systemd 服务。确认博客和 SyncRTC 的既有端口后再分配新端口。

日常发布，由 CD 重复执行

下载/校验产物 → 上传暂存 → 备份/迁移 → 安装版本 → 切换服务 → 健康检查。Nginx、数据库账号、长期密钥不随每次功能发布重建；模型密钥和数据库密码由服务器保管，GitHub 只保存部署所需的受限 SSH 凭据。

建议目录形态：/opt/learning-platform/releases/<commit-sha>/ 放不可变代码与前端产物；/opt/learning-platform/current 指向当前版；用户数据、Parquet 和备份放在 release 目录之外。名称仅为方案，部署前需按服务器实际布局确认。

最容易被忽略的部分：数据库与回退

代码回退可以快；数据库回退不一定可以

前端与 FastAPI 可保留上一版 release，失败时切回旧目录并重启。MySQL 迁移可能已经改写数据，不能假设切回旧代码就自动恢复数据库。首版迁移尽量向后兼容：先新增列/表，代码兼容新旧结构，确认稳定后再另一次发布中清理旧列。破坏性迁移需要停机窗口和经验证的备份恢复步骤。

AI 评分任务与数据属于持久状态

发布或重启 worker 时，未完成的评分任务保留在 MySQL；任务带状态、尝试次数与幂等键，重试不能重复写正式成绩。部署失败不能用旧发布包覆盖新产生的答题记录。

建议的发布失败判定

依赖安装失败、迁移检查失败、systemd 服务未就绪、/api/health 失败、前端资源 404 或权限检查异常，均应停止发布并发出失败状态。自动回退仅覆盖代码/静态资源；涉及已执行的不可逆迁移时，先保持现场并由人决定恢复数据。

按毕设进度实施

  1. 开发前期：本机 Vue + FastAPI + MySQL 跑通题目、答题和打卡；建立最小 CI，先验证构建与测试。
  2. 首次上线：人工准备服务器和子域名，用受控脚本完成首发；记录完整命令与回退点。
  3. 稳定后：加入手动触发 CD，发布同一份 CI 产物；练习一次“前端/API 发布失败 → 代码回退”。
  4. 答辩前：以一个明确提交 SHA 发布演示版并冻结；报告真实线上 URL、版本、健康检查和功能演示证据。
暂不默认自动上线：生产 MySQL 迁移、AI 评分任务和与博客共用的服务器使“每次合入立即部署”多了一层实际影响。等发布、备份、回退都跑通过，再把手动 CD 改为自动。
