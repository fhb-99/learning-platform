毕业设计主线：学习行为分析与可解释复习策略。先让一次真实作答形成可靠数据，再用数据解释“下一次为什么复习这道题”。

01 · 第一件事：定义并实现“一道题的完整旅程”

推荐起点：先写一页验收场景，再实现最小的内容发布与客观题练习流程。从后端题目版本和作答事务起步，通过接口验收后接上 Vue 页面。第一轮就产生后续分析能用的真实记录。
01 管理员发布一道单选题
02 学习者选择方向并领取题目
03 业务后端接收回答、规则判分
04 数据持久化保存作答、成绩与打卡
05 复习调度生成下次复习日期
06 用户反馈看到解析、记录和复习安排

这条流程同时覆盖前端、接口、权限、数据库和业务规则；后续行为分析需要的“谁、何时、做了哪版题、答得怎样、为何安排复习”也在这里产生。

可选起点收益取舍与建议
完整客观题流程迅速验证真实业务，形成可分析数据推荐。首轮界面简洁，重点验证数据和规则
先完成所有页面与后台 CRUD界面进展容易展示可能迟迟没有完整练习；只做第一条流程必要的页面
先做 Agent 聊天与生成演示效果直观尚无可靠题库、成绩和历史可供工具调用，适合后续接入
先研究公开数据与算法较早发现实验数据是否适配若导师要求算法创新可提前；当前适合先做小样本可行性检查，再随系统推进

02 · 你已确认的边界

本轮确认

技术与论文主线

暂无额外硬性技术要求，沿用现有文档；学习行为分析与复习策略是主要答辩亮点。时间比较充裕，具体截止日与每周投入尚未量化，因此本指南按里程碑组织。

本轮确认

统一每日题，个人复习

同一方向、同一本地日期提供同一道题；每个人的完成状态分别记录。个性化先体现在各自的复习队列。

本轮确认

提交当天打卡

合法回答被后端成功接收即计入提交日打卡。AI 次日才评分或评分失败，都不改变当天打卡；失败不记为零分。

本轮确认

可解释的起始复习规则

客观题不强制自评。答错或自评“不会”次日复习；连续答对按 1、3、7、14 天递增，并记录调度依据。这是实验起点，效果尚待验证。

原设计仍保留：计算机与英语两个领域、用户端与管理端、Agent 答疑／出题／正式评分／规划四项能力、DuckDB + Parquet 分析、发布与回退流程。分阶段实现不等于删去最终范围。

本轮澄清补足原设计中每日题唯一性、异步打卡与复习输入的语义。原始两份方案保留；术语集中记录在项目根目录 CONTEXT.md。下述实现拆分、样本量及验收步骤是建议，不代表已编码或已通过验证。

03 · 第一份成果，做到什么程度算完成？

演示脚本：管理员发布一道计算机单选题 → 学习者登录并选择方向 → 领取每日题 → 故意答错 → 看到解析与次日复习安排 → 刷新页面仍保留记录 → 到期后再答一次，形成新的作答记录。

建议只做 4 类页面

登录与方向选择、题目编辑发布、今日任务／答题结果、复习列表／作答历史。一个 Vue 项目区分用户布局和管理布局。

先准备小而可核对的题库

建议用自编或授权的 12 道单选题起步，计算机与英语各 6 道，含答案、解析、知识点与来源。此数量只用于开发验收，不能作为算法有效性证据。

数据库先设计哪些对象？
对象第一轮职责关键边界
User / TrackPreference身份、角色、时区、学习方向从登录身份确定用户，不能信任请求中任意 user_id
Domain / Topic / Track内容归类与适用方向方向与知识分类含义不同，关联关系明确表达
Question / QuestionVersion题目和发布快照作答引用不可变版本，后续编辑不改变旧成绩依据
每日题定义 + 个人完成记录分别表达统一选题和个人进度建议方向／本地日期唯一的题目定义；用户／每日题唯一的个人记录
Attempt / Grade原始回答、规则分数、评分版本新练习追加记录；同一请求重试返回原结果
CheckIn / ReviewPlan提交日打卡、个人下次复习打卡按用户／日期唯一；计划按用户／题目维护
LearningEvent 或等价业务记录为分析保留可追踪事实与作答关联并去重；第一轮无需建设独立事件平台

这是逻辑对象列表，不要求机械地“一行建一张表”。具体字段与迁移在开工时围绕验收场景确定。

最先写的接口与事务

先完成登录鉴权，再依次实现原文已有的发布、领取、提交接口；补充读取复习列表与作答历史的接口。读题接口只返回作答所需信息，答案与解析在允许查看结果时返回。

POST /api/v1/admin/questions/{id}/publish
GET  /api/v1/today?track_id=...
POST /api/v1/attempts

提交时：校验身份、题目版本与幂等键
    → 在同一 MySQL 事务内保存作答、规则成绩、打卡和复习安排
    → 提交成功后返回结果
    → 同一幂等键重试，返回已有提交

建议幂等约束：用户 + 幂等键唯一
建议冲突处理：同一键携带不同回答时拒绝覆盖原记录

网络模型调用不应放进上述数据库事务。主观题阶段再增加持久评分任务与独立 worker。

第一轮必须验证的 6 件事

  1. 版本：题目发布新版后，旧作答仍能展示当时题干与评分依据。
  2. 幂等：同一次提交连续点击或网络重试，只新增一次作答和一次调度；用户主动再次练习可产生新作答。
  3. 事务：提交中途失败，不留下“有成绩但没有对应复习安排”的半成品。
  4. 权限：普通用户不能发布题目，也不能读取另一用户的作答。
  5. 日期：默认 Asia/Singapore，本地午夜边界前后提交归属不同日期，同日多次提交只算一天打卡。
  6. 复习：用固定测试时钟验证答错、自评不会、连续答对及到期领取，逐项比对预期日期。

不必等真实时间过去一天再验证日期逻辑。固定测试时间可以重复检查；浏览器再验证实际操作流程。

04 · 技术栈按任务学，学到能交付就继续

顺序与技术先掌握的内容学习完成的标志
① Python → FastAPI类型、虚拟环境、异常；路由、请求／响应模型、依赖注入、鉴权与接口测试能用 OpenAPI 界面完成读题、提交、查看结果；非法输入被拒绝
② MySQL / InnoDB主外键、唯一约束、索引、事务、版本化迁移重试与并发提交不产生重复记录；空库可通过迁移建表
③ Vue 3 + TypeScript组件、响应式、表单、异步请求、路由；Pinia 管理共享登录状态用户完成上述演示脚本；刷新后从后端恢复业务数据
④ DuckDB + Parquet导出、去重、日期分区、SQL 聚合、结果核对某日作答量与正确率能逐条追溯到业务记录
⑤ Agent 与评分 worker检索、结构化输出、工具授权、持久任务、重试、审计评分有逐点依据；断网／重启后任务状态可靠，恢复不会重复记分
⑥ Nginx / CI/CD前端构建、后端测试、迁移检查、同一产物发布、备份与回退指定版本可部署并验证，失败能按已演练流程恢复

前三项围绕同一条业务流程交替学习。无需先学完所有框架，再开始项目。ORM、迁移工具、UI 组件库、模型服务商和依赖版本还未锁定，开工时做一次兼容性检查即可。

官方资料从哪里读？
  • FastAPI 官方教程：从 First Steps、Request Body、Response Model、Dependencies 与 Security 开始，再读 SQL 与 Testing。
  • MySQL InnoDB 事务模型：用于理解提交、回滚、隔离与并发边界；项目具体 MySQL 版本仍需锁定。
  • Vue 官方快速开始：按官方项目脚手架路线进入，再学习表单、组件和 TypeScript；实现时核对所需 Node 版本。
  • DuckDB 官方 Parquet 文档：可直接查询 Parquet，并从 SQL 结果导出 Parquet；先用自己的小样本练习。
  • FastAPI Background Tasks：理解请求返回后的任务执行方式；本项目正式评分另有持久化、重试和独立 worker 要求，不能只靠一个进程内回调完成。

05 · 按可验收成果推进

  1. 启动：验收脚本、数据样例、仓库边界

    把第一条业务流程与预期结果写清楚；准备两个领域的样题；确认项目独立仓库和开发环境。此时即可列出论文的问题、拟比较策略和需要记录的数据。

  2. 基础：发布 → 作答 → 打卡 → 复习

    交付第 03 节的可运行成果。保留题目版本、作答时间、成绩、调度输入和规则版本。开始最小构建与测试检查。

  3. 主线：行为分析与规则复习

    先从小样本导出 Parquet，核对作答量、正确率、复习到期量；DuckDB 聚合结果写回供看板读取，并显示统计截止时间。定义正确率等指标的分母，待评分题不得算作错误。

  4. 扩展：Agent 四项能力

    建议按题库检索答疑 → 生成待审核草稿 → 持久化正式评分 → 根据已验证指标生成计划接入。正式评分预先做小型可行性验证；完整接入后验证申诉、更正、任务重试与工具撤销。

  5. 验证：对照实验与真实试用

    论文实验协议前置设计，等数据积累后执行。对照固定间隔策略与当前规则策略；公开数据处理实验和本站真实试用分别记录。对 AI 评分另用人工标注集比较误差与争议。

  6. 交付：部署、恢复演练与答辩演示

    依照现有发布方案推进 CI 产物、手动触发 CD、迁移与备份恢复。演示版绑定明确提交版本，并准备无模型密钥或模型不可用时的降级展示。

时间充裕的收益应体现为：更可靠的数据、更清楚的实验和真实试用。当前没有要求增加 Spark、缓存、微服务或在线编程判题。

06 · 让“学习行为分析”成为可证明的亮点

建议研究问题：根据历史表现调整复习安排，是否比固定间隔安排更适合用户完成复习，并在延迟测验中维持答题表现？这是待检验的问题，不能预写“显著提升学习效果”。

要证明什么怎么取证结论边界
系统记录与计算正确选定日期，核对原始作答、去重结果和聚合报表；保留统计截止时间证明数据处理正确，不证明学习效果提高
规则可解释、可复现同一输入与规则版本得到同一计划；页面能解释为什么到期证明调度行为一致，不代表符合真实记忆曲线
策略可能更有效预先约定分组、时长、延迟测验与指标，报告样本量、缺失和不确定性仅比较使用前后分数不能排除题目难度与重复练习影响
能够处理较大数据合法公开数据集单独实验，记录行数、硬件、分区、耗时、内存和重复运行处理吞吐不等于推荐质量；英语数据结果不能直接推广到计算机知识
AI 评分可评估固定题目 rubric、人工标注、模型／提示词版本，统计误差与争议样例小样本一致性不能保证所有开放题正确
第一天就应保留哪些实验输入？

匿名用户标识、题目与版本、领域／知识点、提交时间及当时本地日期、正式分数及评分状态、可选自评、是否复习、原到期时间、实际完成时间、调度前后阶段、规则版本与触发作答。分析导出尽量使用必要字段，原始主观答案不默认进入通用事件日志。

若后来加入推荐排序，先定义推荐候选集、目标与按时间划分的评估方式，再决定是否使用命中率等指标。单纯“下一次复习日期”的策略，不能随意套用 Top-K 推荐指标。历史记录也无法直接给出用户接受另一种复习策略后会发生什么。
